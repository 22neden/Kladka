# Підключення реального сервісу Kladka.UA

## 1. База даних
Створіть Supabase-проєкт. У новій базі виконайте через SQL Editor по черзі:
1. supabase/migrations/202611110001_initial.sql
2. supabase/migrations/202611120001_profile_settings.sql

Якщо перша міграція ВЖЕ виконана — запускайте лише другу. Не запускайте початкову міграцію повторно на заповненій базі. Спершу зробіть резервну копію.
Друга міграція додає професійні поля профілю та таблицю account_settings. Телефон і newsletter_opt_in доступні тільки власнику через RLS. Серверна дата newsletter_changed_at змінюється при зміні згоди; це поточний стан, не незмінний журнал усіх подій.

## 2. Змінні
Скопіюйте .env.example у .env і задайте власні значення:
- EXPO_PUBLIC_SUPABASE_URL
- EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY
- EXPO_PUBLIC_TERMS_URL — HTTPS URL опублікованих Умов Kladka.UA
- EXPO_PUBLIC_PRIVACY_URL — політика приватності
- EXPO_PUBLIC_SUPPORT_EMAIL — ваш контакт підтримки

Не додавайте service_role / sb_secret / пароль бази або Meta App Secret у клієнт чи EXPO_PUBLIC_*.
Якщо обидва параметри Supabase відсутні — локальний режим. Після зміни .env перезапустіть Expo з --clear.

## 3. Email та пароль
У Authentication увімкніть Email provider і Confirm email.
Налаштуйте пароль на сервері: мінімум 9 символів, велика і мала літери, цифри. Клієнтська перевірка не заміняє серверну. Перевірте, які набори літер підтримує ваша серверна політика: клієнт допускає і кирилицю.
Налаштуйте власний SMTP для доставки користувачам, ліміти та захист від масової реєстрації.

Шаблон Confirm signup має містити код, а не лише посилання:

```html
<h2>Підтвердження email — Kladka.UA</h2>
<p>Ваш код: <strong>{{ .Token }}</strong></p>
<p>Введіть його в застосунку. Якщо ви не створювали профіль, ігноруйте лист.</p>
```

Шаблон Reset password:

```html
<h2>Відновлення пароля — Kladka.UA</h2>
<p>Код відновлення: <strong>{{ .Token }}</strong></p>
<p>Введіть код у формі відновлення Kladka.UA. Нікому не повідомляйте його.</p>
```

Відновлення використовує тимчасову непостійну сесію, щоб не відкривати основний застосунок до завершення зміни пароля. Після зміни потрібно увійти знову. Код одноразовий: якщо оновлення пароля не пройшло після перевірки коду, запросіть новий код.
Налаштуйте повторну перевірку/reauthentication для зміни пароля за вимогами вашого Supabase-проєкту. Невідому помилку серверу застосунок показує, а не вважає успіхом.

## 4. Facebook і Google
В Meta Developers створіть app із Facebook Login. App ID та App Secret внесіть у Supabase → Authentication → Providers → Facebook.
Valid OAuth Redirect URI в Meta має точно відповідати callback із Supabase (https://PROJECT.supabase.co/auth/v1/callback). Налаштуйте режим доступності Meta app, тестерів, email permission, сторінки privacy/deletion згідно з вимогами Meta. Не припускайте, що в development mode увійдуть будь-які люди.
Для Google створіть OAuth Web client, заповніть consent screen та внесіть Client ID/Secret у Google provider Supabase.
Supabase Redirect URLs: onlyconstructions://auth/callback і точна адреса /auth/callback опублікованої вебверсії.
OAuth у Expo Go на телефоні не підтримується: тестуйте вебверсію або власну збірку. Email + пароль працює через звичайні API після налаштування сервісу.

## 5. Умови та новини
Потрібні справжні опубліковані Умови. До EXPO_PUBLIC_TERMS_URL соціальний вхід і реєстрація показують пояснення про відсутню конфігурацію. Вхід існуючого email-акаунта не блокується.
При email-реєстрації terms_url, terms_accepted_at та початкова newsletter-згода передаються в metadata. Metadata змінювана користувачем і не є захищеним юридичним аудитом.
Для OAuth користувач бачить текст про створення профілю та посилання на умови; окремий незмінний журнал прийняття умов ще треба зробити перед публічним запуском. Нові OAuth-акаунти не підписуються на новини автоматично.
Сервіс розсилки ще не підключений. У майбутньому він повинен читати поточний стан account_settings, підтримувати відписку з кожного листа і не розсилати користувачам із false.

## 6. Фото, модерація, видалення
Початкова міграція створює public portfolio та private chat-images. Фото профілю зберігається у portfolio в папці власника. Текст, фото та професійні дані профілю публічні для зареєстрованих користувачів; телефон окремий і приватний.
Нові оголошення мають moderation_status=pending. Адміністратор перевіряє їх у Supabase Dashboard і встановлює approved/rejected. Не видавайте користувачам service role для обходу перевірки.
Розгорніть supabase/functions/delete-account. Секрети SUPABASE_URL і SUPABASE_SERVICE_ROLE_KEY доступні лише серверній функції. Видалення має бути перевірене на тестовому акаунті, включно з медіафайлами.
Старі замінені аватари можуть залишатися у Storage до видалення акаунта; планове очищення невикористаних фото — окреме завдання.

## 7. Перевірка двома користувачами
A реєструється, підтверджує email, заповнює профіль, публікує оголошення. Адміністратор схвалює. B входить окремим акаунтом, бачить профіль/оголошення, починає чат. A і B обмінюються текстом/фото. Перевірте ізоляцію телефону, блокування, відписку, повторний вхід, видалення.
Цю перевірку в живому Supabase ще не виконано: доступи не надані.
